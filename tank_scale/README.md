正式目标见根目录 [SPEC.md](../SPEC.md) 与 [GOAL.md](../GOAL.md)：名义 340 L 圆形聚乙烯缸，内径 39 in，缸深 20 in；实际水深、水量尚未确认。

实际部署前需明确节点位置、传感器清单、校准与补偿、供电余量/保险丝/隔离参考地、防水与固定接线，并完成 UTC、MQTT、原始数据存储、断线恢复及长期测试。

本目录没有批准新的硬件、接线或采样参数。后续经确认再增加实际节点和部署记录。

## 方法与原理

### 方法：从台架到实际缸怎么走

台架（lab_scale）已经验证的是"数据链路"：探头 → ESP32 → Wi-Fi/MQTT → 网关 → 数据库 → 网页，以及断线重发、重启恢复。实际部署要在这条链路上补齐 SPEC 要求的其余部分，顺序大致为：

1. 按 SPEC §5 确定节点位置和分工（MID 中层代表站、BOTTOM 底层风险站、H2S、BYPASS 旁路），把台架的 Node-1/Node-2 映射到正式编号，或按需增加节点。
2. 补齐台架未完成的部分：局域网 UTC 源（NTP）、断电不丢的缓冲、探头校准与温度/盐度补偿、把 broker 和数据库迁到 Raspberry Pi 并开机自启。
3. 按 SPEC §9–§17 做供电与接线验收：12 V / 5 V / 3.3 V 电源域、保险丝、隔离参考地、固定接线、防水与防盐雾。
4. 按 SPEC §47 做验收：真实测量走完全链路，并经受 ESP32 重启、Wi-Fi 中断、MQTT 重连、临时断网，全程保留时间戳、序号、QC 和原始数据。

### 原理：为什么单独分目录

- **台架不等于部署**。台架用的是手头的板子和电源（例如 ESP32-S3 N16R8 而非 SPEC 首选的 N8R8、无保险丝的 12 V 电源），这些是"能跑通"的现状，不是安全或科学验收。把它们和正式部署记录混在一起，会让"验证过的"和"临时凑合的"分不清。
- **正式设计以 SPEC 为准**。tank_scale 里将来的每一项硬件都要有 LOCKED / RECOMMENDED / VERIFY BEFORE PURCHASE 之类的状态，未核实的厂家参数标 NOT VERIFIED，不能因为台架用过就自动升级为 LOCKED。
- **固件架构不变**。SPEC §43 要求换网关不改固件；台架验证过的 MQTT 主题和 ACK 约定就是部署时继续沿用的接口。

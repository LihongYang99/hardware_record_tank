# camera_node — 水下 PoE IP 相机

**当前状态（2026-09-27 晚）**：相机有线接实验室路由器，视频已接入 Jetson 网页（子码流 704×576，约 5 帧/s 预览，不录像）。Jetson 重启后要重新执行 `sudo ip addr add 192.168.1.200/24 dev enP8p1s0`，当晚执行后画面恢复（`LIVE`）。详见 [PROGRESS.md](PROGRESS.md)。

已记录 Barlus 相机和 TP-Link/Omada POE150S 注入器商品参数。2026-09-22 实物标签显示相机型号 IPC5MPIR-PBX10、默认 IP 192.168.1.88；用户修正 Jetson 临时地址后报告 ping 已有回应。最终 MAC 对照和视频流仍待验证；商品型号对应关系见 HARDWARE.md。

**重要：当前 304 相机标明淡水用途；不能批准用于项目 15–25 ppt 的长期盐水浸泡。** 规格来源、冲突和验证边界见 HARDWARE.md。

## 方法与原理

### 方法：画面是怎么到网页的

1. **供电与网络**。相机只有一根网线，经 PoE 注入器同时供电和传数据，接到实验室路由器。相机固定 IP `192.168.1.88`，与节点所在的 `192.168.88.x` 不是一个网段，所以 Jetson 的有线网卡要临时加一个 `192.168.1.200/24` 地址才能访问它（每次重启或重插网线后要重做）。
2. **找到视频地址**。`jetson_web/camera_onvif.py` 通过 ONVIF 标准协议向相机询问（`GetStreamUri`），由相机自己返回 RTSP 地址，不靠猜路径。地址含账号字段，只写进本机私有的 `.env`（Git 忽略），网页和日志都不显示。
3. **解码**。`jetson_web/server.py` 用 GStreamer 建立一条管道：`rtspsrc`（TCP）→ 拆 H.264 → 解码（Jetson 上用硬件解码器 `nvv4l2decoder`，否则软件解码 `avdec_h264`）→ 缩放并降到 5 帧/s → 编成 JPEG → 保存最新一帧在内存。用的是子码流 704×576。
4. **显示**。浏览器每约 2 s 向网关的 `/camera.jpg` 取一张 JPEG。超过 10 s 没有新帧就不显示旧画面；管道出错后 5 s 自动重连。不录像、不存盘、无音频。

### 原理：为什么这样做

- **为什么用 ONVIF 而不是手动填地址**：不同厂商的 RTSP 路径和端口各不相同，猜错了只会得到"连不上"，无法区分是地址错还是网络错。ONVIF 是 IP 相机的通用管理协议，能直接问出相机自己的配置（码流、分辨率、编码格式），结果可核对、可记录。
- **为什么用 RTSP over TCP**：局域网内 TCP 不会因为丢包出现花屏，代价是延迟略高（设定 200 ms 缓冲），对监测预览可以接受。
- **为什么用子码流**：主码流 1920×1080 25 fps 6 Mbps，对看"虾在不在动、水浑不浑"是浪费；子码流 704×576 1.5 Mbps 足够，解码和网络开销都小。
- **为什么服务器转 JPEG 让浏览器轮询，而不是直接推视频流**：浏览器不能直接播 RTSP，做成 WebRTC/HLS 需要额外软件；而网页服务只用 Python 标准库，"每 2 秒一张 JPEG"最简单、最容易排错。监测用途不需要流畅视频。
- **为什么要写明确的 H.264 管道**：GStreamer 的自动解码（`uridecodebin`）在 Jetson 上会选硬件解码器，它输出的是 NVMM 显存格式，接不上普通的 `videoconvert`，结果是"连上了但一直没画面"。明确指定 `nvv4l2decoder ! nvvidconv` 才能出图。相机若改成 H.265 就要改管道。
- **为什么时间只用 Jetson 取帧时间**：相机自己的时钟差约 6 个月（设了 NTP 但局域网没有 NTP 源），画面上的时间不可信。
- **为什么不批准盐水部署**：商品和厂家页面都写明 304 不锈钢版本用于淡水；IP68 只说明防水，不代表耐盐腐蚀。目标盐度 15–25 ppt 下长期浸泡需要厂家书面确认或换型号。
- **安全边界**：相机目前允许匿名 ONVIF 查询并返回带账号的 RTSP 地址，同一局域网内任何设备都能看画面。后续应改默认密码、关闭匿名 ONVIF；网页服务本身不向外泄露地址。

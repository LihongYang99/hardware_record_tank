## 控制与校准（Jetson 终端）

在 `lab_scale/jetson_web` 目录运行。每条命令只发一次，等泵的真实回复再显示结果。

**设备控制页（需要登录）**：中文 `http://192.168.88.249:8080/control`，英文 `/control/en`。监控页 `/` 不需要登录，只读；控制单独在这个页面，按设备列出（目前只有泵 1），登录后可以"启动 / 改流速"和"停止"，并看到最近 15 条操作（含终端操作；网页不能校准）。准备：① 在 Jetson 为每个操作员建账号 `python3 pump_ctl.py web-user add <账号>`（`web-user list` 查看、`web-user remove <账号>` 删除，删除后已登录的会话立即失效；只存加盐哈希）；② 网页服务带 `--pump-control` 启动。操作记录里操作人为 `web-<账号>`。同一账号连续输错 5 次锁 60 秒，30 分钟不操作自动退出。实验室局域网内是明文 HTTP（校外经 SSH 转发是加密的），不要把这个密码用在别处。

终端命令：

```bash
python3 pump_ctl.py show                 # 当前状态、设定流量、校准状态、最大恒定流量
python3 pump_ctl.py start 50             # 恒定 50 mL/min（DC,50.00,*），设定存进板子，断电后恢复
python3 pump_ctl.py stop                 # 停止（X），设定清零
python3 pump_ctl.py query maxrate        # 查最大恒定流量（DC,?）；另有 state / cal / volume / voltage / status
python3 pump_ctl.py dispense 10          # 输送 10 mL（校准用）
python3 pump_ctl.py dispense 10 --minutes 1                          # 1 分钟内输送 10 mL（按时间校准用）
python3 pump_ctl.py --note "10mL量筒 淡水 气泡已排" calibrate 9.8   # 写入实测 9.8 mL
python3 pump_ctl.py --note "原因" cal-clear                          # 清除校准
```

**校准步骤**（数据手册 p.77–78；用淡水，不用盐水或化学品）：

1. 接好 12 V，软管进水端放进一杯淡水，出水端放进另一个杯子。
2. `start 50` 让泵转一两分钟，边转边轻敲软管，把气泡全部排出；然后 `stop`。
3. 出水端换成**干净的量筒**（至少 10 mL，刻度准确），或放在分辨率 0.1 g 的电子秤上的杯子（先去皮；淡水 1 g = 1 mL）。
4. `dispense 10`，等泵停下（网页或 `show` 显示已停止）。
5. 读出实际体积，例如 9.8 mL，运行 `--note "…" calibrate 9.8`。工具会显示校准前后状态和新的最大恒定流量。
6. 恒定流量模式建议再做一次"按时间"校准：`dispense 10 --minutes 1` → 量 → `calibrate <实测>`。两种校准互相独立，`query cal` 回 `?CAL,3` 表示两种都做过。
7. 手册建议体积大于 5 mL；可以重复几次取平均。

每条命令（谁、什么时间、什么命令、泵的回复、备注、校准前后）都记在数据库 `operator_event` 表和 `raw_log` 里。

## 方法与原理

### 方法：怎么控制和监测泵

1. **硬件链路**。泵的五芯数据线直接接 ESP32：红 VCC → 3V3，黑 GND → GND，白 RX → GPIO17（ESP TX），绿 TX → GPIO18（ESP RX），蓝 INT → GPIO4。电机另由 12 V 适配器供电，不经过 ESP32。详见 [WIRING.md](WIRING.md)。
2. **协议**。EZO-PMP 出厂就是 UART 模式，9600 bps / 8N1，ASCII 文本命令，和 Node-2 的 Atlas EC/pH 电路是同一套格式（`?` 开头的查询回复、`*OK` 应答）。
3. **启动**。关掉出厂的每秒连续输出，查身份（必须是 `PMP`）、重启原因、校准状态、上电自动输送设置、最大流量。都只读，不改泵的存储设置。
4. **控制**。操作人在 Jetson 上运行 `pump_ctl.py`，经 MQTT 发一条带编号的命令；固件只执行白名单里的命令（恒定流量启动、停止、定量输送、校准、只读查询）。流量设定存进 ESP32 的 NVS，泵复位或断电后自动恢复。
5. **每 4 s 监测**。查运行位 `D,?`，同时读 INT 引脚；查电机电压 `PV,?`、本次上电累计体积 `TV,?`；合成一行结果，原始回复原样附在行里。
6. **上传与显示**。与 Node-1/2 相同：RAM 队列 → Wi-Fi/MQTT → Jetson 落库后 ACK → 监控页"04 / PUMP 1"面板和设备控制页显示"运行中 / 已停止"、电机电压和累计体积。

### 原理：为什么这样设计

- **为什么要旁路泵**。SPEC §29–§30 要求建一个小旁路：从缸里抽一小股水，流过流通池里的 Mg、Ca 等传感器再回到缸里。有些传感器需要稳定水流、方便取出维护，放在旁路比直接泡在缸里合适。泵是旁路的动力，它停了，旁路里的读数就不再代表缸里的水。
- **为什么是蠕动泵**。蠕动泵靠滚轮挤压软管推水，液体只接触软管：不污染样品、不被盐水腐蚀泵体、低流量下每转排量固定，流量容易控制（Phase-1 已比较隔膜泵和离心泵）。代价是软管和泵头会磨损，要定期更换（手册标称软管约 1,000 h）。
- **为什么用恒定流量 `DC` 而不是 `D,*`**。`D,*` 固定以最快速度（约 105 mL/min）运行；`DC,<流量>,*` 让控制器自己调节到设定值。这台泵未校准时恒定流量上限是 54.66 mL/min，校准后由泵重新确定。旁路流量要够让传感器看到新鲜水，又不能大到搅动缸底、加长回流，SPEC 给的范围是 50–150 mL/min。
- **为什么要反复重发设定**。手册写明：连续模式运行 20 天后泵会自行复位，复位后就停了。固件把"收到 `*RS`/`*RE`"和"泵报告停止"都当成需要重发的信号，这样无人值守时泵也能自己恢复，而且每次复位都有记录（`pump_resets`）。
- **为什么"运行中"要两路核对**。`D,?` 是控制器的软件状态，INT 引脚是它输出的硬件电平，两者不一致说明线路或泵有问题（`STATE_MISMATCH`）。再加电机电压：控制器说在转但电压不到 10.8 V，说明 12 V 没接或掉了（`MOTOR_VOLTAGE_LOW`）。但这些都只能说明"控制器在让电机转"，**不能证明软管里真有水在流**，所以网页明确写"控制器报告"。真正的水流要等流量计。
- **为什么用 UART 直连、不做隔离**。UART 简单，和 Node-2 的 Atlas 代码同一套思路。Phase-1 设计的隔离 I2C 是为同一总线上会接触流体的流量计准备的；蠕动泵的水只碰软管，不和电路形成回路。以后这个节点加接触流体的传感器时，那一路要重新隔离。
- **为什么单独一块 ESP32**。泵是执行器，其他节点是传感器。分开以后，泵的故障、复位或调试不会影响 DO/ORP/EC/pH 采集，反过来也一样，这与 SPEC §39 "单个设备故障不能冻结整个节点"一致。
- **为什么监控和控制分成两个页面**。看数据不影响设备，所以监控页谁都能看、不需要登录；控制会改变实验条件，所以单独一个页面，必须用个人账号登录，每条命令都记到具体的人。控制页只开放启动和停止；校准要配合量筒逐步操作，放在终端。所有命令最终都经 broker 里唯一有权限的 `pump-operator` 账号发出（节点自己、接收器、其他节点都不能写泵的命令主题）。
- **为什么每条命令带编号、只等一次回复**。MQTT QoS 1 可能重复投递，重复执行"输送 10 mL"会让校准错一倍，所以固件按编号去重。节点离线时命令直接丢弃，不会在之后突然执行。

## 调试过程（2026-09-27，摘要）

从建立节点到网页控制在同一天完成。下表按发生顺序列出遇到的每个问题、查明的原因和处理方式，逐条原始记录（时间、原文回复、体积）在 [PROGRESS.md](PROGRESS.md)。

| # | 现象 | 原因 | 处理与结论 |
|---|---|---|---|
| 1 | 接好线、还没烧录时，板上灯"红绿蓝交替闪烁" | 是新 ESP32 出厂演示程序的板载 RGB 灯，不是泵的状态灯（泵灯：UART 待机绿、I2C 待机蓝、灭 = 没电） | 烧录后该灯停止。看泵状态要看泵控制板上的灯 |
| 2 | `build_node1.py --node 4 --check` 只编出 482 KB | 全零 MAC 让编译器判定身份检查永远不通过，把之后的 Wi-Fi/MQTT/泵代码整段删掉 | 用虚拟 MAC 复编译得 912 KB 才是真实大小；`--check` 产物不烧录 |
| 3 | 烧录后 Wi-Fi、MQTT 正常，泵对 `*OK,1` 无回复，只在开机收到 1 个 `00` 字节；泵灯不亮 | 泵控制板没有上电（用户确认电源接错，具体接法未记录） | 改正后立刻收到 `*RS`/`*RE`，初始化全部通过。教训：串口不通先看泵灯是不是绿 |
| 4 | 12 V 未接时下发 `DC,80` | 泵回 `*UV,PUMPPWR,0.00` + `*ER`（电机欠压，拒绝启动） | 固件记 `CONTROL_REJECTED`，结果行 `QC=NOT_RUNNING_AS_COMMANDED`；属正常保护，不是故障 |
| 5 | 原定固定 80 mL/min | 泵报告未校准的恒定流量上限 `?MAXRATE,54.66` | 用户决定自己控制：固件 0.2 默认 0（不转），流量由操作员设定并存 NVS，泵复位后自动恢复 |
| 6 | 第一次 `calibrate 9.8`，泵 16 ms 内回 `*ER` | 本次上电没有输送过（`TV` 0.00），泵拒绝 `Cal` | `pump_ctl.py calibrate` 加检查：上一条操作必须是成功完成的 `dispense`。正确顺序：`start` 排气 → `stop` → `dispense 10` → 量 → `calibrate` |
| 7 | `dispense 10` 实测 8.3 mL（−17%，远超手册未校准 ±5%） | 出厂系数与本机软管、进水条件不符（量筒读数误差也占一部分） | `Cal,8.30` → `?CAL,1`。校准后同样的 `D,10` 耗时从 5.99 s 增到平均 7.03 s（×1.17 ≈ 10/8.3），证实校准生效 |
| 8 | 校准后 `dispense 10 --minutes 1` 仍是 8.3 mL | 按时间输送用另一套"按时间"校准系数，两种校准互相独立 | 再次 `Cal,8.30` → `?CAL,3`；`?MAXRATE` 54.66 → 45.36。复核 9.7 mL（−3%；10 mL 量筒读数本身约 1–2% 不确定度，单次测量不能区分泵与读数） |
| 9 | `calibrate <8.3>` 报 bash 语法错误 | 尖括号被 shell 当成重定向 | 去掉尖括号重发；出错的那条没有发出，泵无变化 |
| 10 | 想停泵 | — | 用 `stop`，不要拔 12 V：设定仍在 NVS，固件每分钟重试，12 V 一接回泵就自己转 |
| 11 | 固件 0.2 烧录前复查 | 操作命令日志可能把别的命令的回复记成本条的回复；上一次输送迟到的 `*DONE` 可能被当成查询的回复 | 日志改为显式传入回复；操作命令阶段迟到的 `*DONE` 只记 `DISPENSE_DONE`、不当回复。主机测试覆盖后再烧 |
| 12 | 监控页"设定流量"卡片一直空 | 接收器 `run_mqtt.py`（16:42 EDT 起）启动时 `server.py` 的参数表还没有 `target_mL_min`；接收器启动时导入参数表，之后改了不跟着变。原始行里有，`measurement` 表里没有 | 20:21 EDT 重启接收器后入库。规则：改了 `server.py` 的 NODES/SENSORS，`run_mqtt.py` 和 `server.py` 都要重启 |
| 13 | 网页控制先后改了三版 | ① 监控页泵面板加操作密码开关（写完未启用）→ ② 用户：监控不该要登录、控制要账号密码 → ③ 用户：以后多台设备，泵叫泵 1 | 最终：监控页只读；单独登录页按设备列卡片（`pump_ctl.DEVICES`）；每条操作记操作人和泵回复 |
| 14 | "控制页改成中文"之后又问"怎么还是中文" | 需求是英文页 | 做成中英两版 `/control`、`/control/en`，右上角切换 |
| 15 | Jetson 14:12 EDT 重启后约 4 小时没有数据 | broker、接收器、网页都没有开机自启，节点 RAM 缓冲只有约 2 分钟 | 16:42 EDT 手动启动后恢复；12:42–16:42 EDT 的数据已丢失。待办：开机自启 |

自动测试也在迭代中改过两处：锁定测试最初写成 4 次失败即锁，实际是成功登录清零计数、连续 5 次失败才锁，按设计改测试；`control.js` 一个内层变量与外层的电压变量同名，改名。最终 Python 测试 18 项、固件主机测试全部通过。

# Node-7 — 加热器（水温控制）

## 身份

- 固件标识：`shrimp-node07`；单独一块 ESP32-S3（esptool 2026-10-12：QFN56 rev v0.2，内置 8 MB PSRAM，16 MB flash）。
- MAC：`44:1B:F6:FE:73:48`（已写入固件 `NODE_MAC`）。IP：`192.168.88.245`（2026-10-12 Jetson ARP，DHCP；需要在路由器上做静态租约）。
- 执行器：双路 IoT 交流电源继电器（Two-Channel Control IoT AC Power Relay Module），加热器插在 **CH1 的常断（normally OFF）插座**。具体型号未记录（NOT VERIFIED）。
- 数据库传感器编号 `HEATER_RELAY`（参数 `relay_on`）；控制页卡片"加热器"。决策记录 DECISION 052。

## 怎么控温

1. 登录控制页 `http://192.168.88.249:8080/control`，在"加热器"卡片填设定温度（5–32 °C），点"保存温度"。
2. 点"打开自动控温"。**只有这个开关打开时才会自动加热**；关闭时加热器始终断电。
3. 水温 = Node 1 DO 探头温度与 Node 6 浊度探头温度的平均值。低于设定温度就通电，达到设定 + 0.5 °C 断电。
4. 卡片上能看到平均水温、两个探头各自的读数、继电器状态和当前原因（如"低于设定温度：加热中""读数过期：DO_SEN0681"）。每次通电 / 断电、改设定、开关自动控温都记在"最近操作"。

## 方法与原理

### 方法

- **谁做决定**：网关（Jetson，`heater_ctl.py`）每 10 s 读两个探头的最新温度，算平均，按设定温度决定开或关，经 MQTT 发 `HEAT,ON` / `HEAT,OFF` 给 Node 7。Node 7 只执行这两条命令，用 GPIO5 驱动继电器 CH1 的控制输入。
- **一直确认才保持通电**：开启期间网关每 20 s 重发一次 `HEAT,ON`；Node 7 在 60 s 内没收到就自己断开继电器。
- **为什么接常断插座**：继电器控制端没有信号时这个插座就没电。ESP32 掉电、重启、跑错程序、线松了，加热器都是断电状态。

### 原理：为什么这样设计（都是"出问题就断电"）

- **数据不可信就不加热**：任一探头没有读数、读数超过 30 s 没更新、QC 不正常、超出 0–40 °C，或两个探头相差超过 3 °C，都直接断电，不用单个探头凑合。
- **回差**：低于设定开、高于设定 + 0.5 °C 才关，避免温度在设定值附近时继电器频繁开合。
- **网关停了也安全**：Jetson 重启、网页服务没运行、broker 停止、Wi-Fi 断开，都会让 `HEAT,ON` 停止到达，60 s 内自动断电。网页服务必须带 `--pump-control` 启动控温才会运行。
- **"通电"不等于"在加热"**：网页显示的是节点给继电器的控制状态，不是测得的电流；加热器自身的温控器、保险或故障都看不到。

**注意**：浊度探头的温度通道没有资料给出精度（DECISION 050 原本不把它当水温用），这里按用户要求参与平均；两个探头相差超过 3 °C 时停止加热就是为此设的保护。浊度探头戴保护盖或不在水里时，读到的是空气温度，会被"相差过大"挡住，加热器保持断电。
